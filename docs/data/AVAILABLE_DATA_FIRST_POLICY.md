# Available-data-first policy

Before claiming a material data gap or recommending new measurement, check and document the available evidence that could answer the named decision. “Not packaged in this checkout” is not `DATA_DO_NOT_EXIST`; source-internal evidence has scientific value but is not independent external validation.

For substantive G1–G3 work, inspect `puckworks/data/MANIFEST.csv`, `puckworks/data/AVAILABLE_DATA_REGISTER.json`, relevant cards, external-corpus status, and prior task artifacts. G0 work may record `NOT_APPLICABLE`. A shortage statement must name the observable, decision, required directness and independence, and evidence checked. Do not use “the programme is data-starved” as a complete conclusion.

Before laboratory escalation, consider direct comparison, reconstruction, source-internal transfer, normalized comparison, compatible joins or adapters, sensitivity, identifiability/discrimination, a fair baseline, and a bounded public-data search. “Exhausted” means exhausted for the named decision. Any recommendation must identify the unresolved join, why existing data cannot supply it, the minimum marginal-value measurements, source-apparatus evidence already available, local qualification still required, and whether the objective is closure or independence.

Puckworks owns MANIFEST provenance, cards, capabilities, external-corpus identities, directness, validation strength, rights, and eligible/blocked uses. External raw data remain external; resolve them by explicit CLI path, `PUCKWORKS_EXTERNAL_DATA_ROOT`, `~/.config/puckworks/data_sources.json`, or their public locator. A missing mount is `KNOWN_EXTERNAL_CORPUS_NOT_CURRENTLY_MOUNTED`, not absence.

The preflight is one artifact inside the substantive task, not a new lifecycle stage. It does not authorize purchase, spending, laboratory contact, quotations, shipping, collection, or protected scoring; those actions retain separate owner authorization.
